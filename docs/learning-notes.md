## ステップ1:プロジェクトの作成

### 1-1. 使ったコマンドと、各オプションの意味

```bash
npx create-next-app@latest . --typescript --tailwind --eslint --app --src-dir --import-alias "@/*" --use-npm
```

| 部分 | 意味 |
|---|---|
| `npx create-next-app@latest` | **Next.js** の最新版で、プロジェクトの雛形を作る |
| `.` | 今いるフォルダにそのまま作る(新しいサブフォルダは作らない) |
| `--typescript` | **TypeScript** で作る |
| `--tailwind` | **Tailwind CSS** を設定済みにする |
| `--eslint` | **ESLint** を設定済みにする |
| `--app` | **App Router** を使う |
| `--src-dir` | コードを `src/` フォルダの中に置く |
| `--import-alias "@/*"` | `@/` から始まる短い書き方で `src/` 内のファイルを読み込めるようにする |
| `--use-npm` | パッケージ管理に **npm** を使う |

ポイントは、これらの選択を最初にコマンドで決めておくと、あとから設定し直す手間が省けることです。

### 1-2. 生成されたファイルの役割

| ファイル / フォルダ | 役割 |
|---|---|
| `package.json` | プロジェクトの設計図。使うライブラリと、`npm run dev` などのコマンドが書かれている |
| `package-lock.json` | 実際に入ったライブラリのバージョンの記録。手で編集しない |
| `src/app/page.tsx` | トップページ(`/`)の中身 |
| `src/app/layout.tsx` | 全ページ共通の枠(HTMLの外側) |
| `src/app/globals.css` | 全体のCSS。Tailwind CSSの読み込みもここにある |
| `tsconfig.json` | TypeScriptの設定 |
| `next.config.ts` | Next.js自体の設定 |
| `eslint.config.mjs` | コードの書き方チェックの設定 |
| `.gitignore` | Gitの管理に入れないファイルの一覧 |
| `AGENTS.md` | Next.jsが自動で作る、AIツール向けのメモ。アプリの動作には関係しない |
| `node_modules/` | 入れたライブラリの実体。大量にあるので触らない。Gitにも入れない |
| `.next/` | 実行時に自動生成される作業ファイル。触らない。Gitにも入れない |

### 1-3. `.gitignore` と秘密情報

`.gitignore` には `.env*` という行がある。これは、`.env` で始まるファイルをGitの管理対象から外す設定である。

後のステップで、Slack Incoming Webhook の URL を `.env.local` というファイルに書く。このURLを知っている人は誰でもSlackのチャンネルに投稿できるため、リポジトリに入れてはいけない。`.env*` が最初から無視される設定になっているので、達成基準の「Webhook URL がリポジトリにコミットされていない」を満たしやすい状態になっている。

### 1-4. 脆弱性の警告との付き合い方

`npm install` の最後に `5 high severity vulnerabilities` と表示された。

- `npm audit fix --force` は、バージョンを強制的に変える。プロジェクトが動かなくなる可能性があるため、内容を確認せずに実行しない。
- 警告の内容は `npm audit` で確認できる。開発時にしか使わないツールが原因のことも多い。
- 学習用のプロジェクトでは、まず動かして内容を理解することを優先する。公開するアプリでは、ここを見直す。

### 1-5. 開発サーバーで動作確認する

```bash
npm run dev
```

- **開発サーバー** が起動し、`http://localhost:3000` で画面を確認できる。
- コードを保存すると、ブラウザが自動で更新される。
- 止めるときは、ターミナルで `Ctrl + C` を押す。

Next.jsの初期画面(「To get started, edit the page.tsx file.」)が表示されれば、プロジェクトの作成は成功である。

## ステップ2:フォーム画面の作成

ここでは「見た目」だけを作り、送信処理はまだ入れていない。

### 2-1. 作ったもの

| ファイル | 内容 |
|---|---|
| `src/components/contact-form.tsx`(新規) | 3項目のフォーム本体(名前、メール、内容、送信ボタン) |
| `src/app/page.tsx` | 初期画面を削除し、カードの中にタイトル、説明文、フォームを置いた |
| `src/app/layout.tsx` | `lang="ja"` に変更し、タブのタイトルを「お問い合わせ」に変更 |
| `src/app/globals.css` | 日本語フォント(Hiragino Sans、Yu Gothic UI、Meiryo)を指定 |

### 2-2. ページと部品を分ける理由

`page.tsx` は「ページの組み立て」、`contact-form.tsx` は「フォームという部品」を担当する。部品を分けておくと、次のステップでフォームに機能を足すときに、`page.tsx` を触らずに済む。

### 2-3. Tailwind CSS の考え方

- `rounded-lg`(角を丸くする)、`px-3.5`(左右の余白)のような小さなクラス名を、HTMLの `className` に並べて見た目を作る。
- `dark:` を前に付けたクラスは、PCがダークモードのときだけ有効になる。例:`bg-white dark:bg-zinc-900`
- `focus:` を前に付けたクラスは、入力欄にカーソルが入っているときだけ有効になる。このフォームでは、緑の枠線を出している。
- 長いクラス名を3回書くのを避けるため、共通部分を `fieldClass` という変数にまとめた。見た目を変えたいときは、変数の1か所を直せばよい。

### 2-4. フォームの作りで押さえたこと

| 項目 | 内容 |
|---|---|
| `label` の `htmlFor` と、`input` の `id` | 同じ名前にして結び付ける。ラベルの文字をクリックしても入力欄が選択され、スクリーンリーダーが項目名を読み上げられる |
| `name="name"` など | 次のステップで、送信内容を項目名ごとに取り出す目印になる。入れ忘れると、値が取り出せない |
| `type="email"` | スマートフォンでメール用のキーボードが出る |
| `noValidate` | ブラウザ標準のチェックを止める。チェックとエラーメッセージは、zodで自分で決めるため |
| `event.preventDefault()` | フォームの標準動作(ページの再読み込み)を止める。今は送信処理がないための暫定対応で、ステップ3〜4で置き換える |

### 2-5. `"use client"` とは

Next.js(App Router)の部品は、初期状態では「サーバー側で組み立てる部品(サーバーコンポーネント)」になる。ボタンを押したときの処理や、エラー表示のように「ブラウザ上で動く」機能を持たせたい部品は、ファイルの先頭に `"use client"` と書いて、ブラウザ側の部品(クライアントコンポーネント)にする。

このフォームは、次のステップでエラーメッセージを画面に出すため、今のうちに `"use client"` を付けた。

### 2-6. 見た目で気を付けたこと

- **ボタンの色**:ライトモードは濃い緑に白文字、ダークモードは明るい緑に黒文字にした。明るい緑に白文字だと、文字が読みにくくなる(コントラストが不足する)ため。
- **日本語フォント**:雛形の設定は日本語フォントを持たない `Arial` だった。日本語を含むフォントの並びに変更した。
- **開発用の「N」アイコン**:画面の左下に出るNext.jsの丸いアイコンは開発中だけの表示で、本番では出ない。

## ステップ3:zodによるバリデーション

入力内容が正しいかを、サーバー側でチェックし、エラーを画面に表示する。

### 3-1. 準備:zodのインストール

```bash
npm install zod
```

入ったバージョンは 4.6.7。**zod** は、バージョンによって書き方が変わる。Next.jsのドキュメントの例には、古い書き方(`error.flatten()`)が載っていた。そこで、実際に入ったバージョンの型定義を確認し、新しい書き方(`z.flattenError()`)を使った。

### 3-2. 作ったもの

| ファイル | 役割 |
|---|---|
| `src/lib/contact-schema.ts`(新規) | 入力ルール、エラーメッセージ、結果の型を1か所にまとめたもの |
| `src/app/actions.ts`(新規) | 「送信する」を押したときに、サーバー側で動く処理(**Server Action**) |
| `src/components/contact-form.tsx`(更新) | エラーを画面に表示するように変更 |

### 3-3. 入力ルール(スキーマ)

| 項目 | ルール | エラーメッセージ |
|---|---|---|
| お名前 | 1〜50文字(前後の空白は無視) | 「お名前を教えてください」「お名前は50文字以内でご入力ください」 |
| メールアドレス | メール形式 | 「メールアドレスをご確認ください」 |
| お問い合わせ内容 | 10〜1000文字(前後の空白は無視) | 「お問い合わせ内容を10文字以上でご入力ください」「お問い合わせ内容は1000文字以内でご入力ください」 |

- `.trim()` で前後の空白を取り除くので、スペースだけの入力は「空欄」として弾かれる。
- `z.infer<typeof contactSchema>` で、ルールからデータの型を自動で作れる。ルールと型がずれない。
- 文言を変えたいときは、`contact-schema.ts` だけを直せばよい。

### 3-4. チェックをサーバー側で行う理由

ブラウザ側のチェックは、開発者ツールなどで回避できる。サーバー側でも必ずチェックしないと、不正な入力がそのまま通ってしまう。そのため、チェックは Server Action の中で行う。

### 3-5. Server Action の流れ

1. ユーザーが「送信する」を押す。
2. フォームの入力内容が、`FormData` として `submitContact` に渡される。
3. `formData.get("name")` のように、`input` の `name` 属性の名前で値を取り出す。(`name` を付けておく必要があった理由)
4. `safeParse` で、ルールに合っているかを調べる。**`safeParse`** は、違反してもエラーで止まらず、結果(成功か失敗か)を返す。
5. 失敗なら、`z.flattenError` でエラーを「項目名ごとのメッセージ一覧」に整えて返す。
6. 成功なら、成功の結果を返す。(ステップ4でここにSlack通知を追加する)

### 3-6. 画面側:`useActionState`

- **`useActionState`** は、Server Action の結果を `state` として受け取る。`state`(結果)、`formAction`(formに渡す関数)、`pending`(送信中か)の3つが返る。
- `<form action={formAction}>` にすると、送信時に Server Action が呼ばれる。ステップ2の `onSubmit` と `preventDefault` は不要になった。
- エラーがある欄は、枠線が赤くなり、欄の下にメッセージが出る。
- `disabled={pending}` で、送信中はボタンを押せなくなり、二重送信を防げる。

### 3-7. 入力内容が消えないようにする工夫

フォームは、送信後に入力欄が空に戻ることがある。エラーのたびに入力が消えると、ユーザーが困る。そこで次の対応をした。

- エラー時に、入力した内容(`values`)も一緒に返す。
- 入力欄の `defaultValue` に、その値を入れる。
- 成功したときだけ、空の値を返して、入力欄を空に戻す。

### 3-8. アクセシビリティ(使いやすさ)への配慮

- `aria-invalid`:入力欄がエラー状態であることを、スクリーンリーダーに伝える。
- `aria-describedby`:入力欄と、その下のエラーメッセージを結び付ける。
- エラーの文字色は、ライトモードとダークモードで、読みやすい濃さを変えている。

### 3-9. 動作確認の結果

次の5つを確認し、すべて想定どおりだった。

1. 何も入力せず送信:3つの欄にエラーが出る。
2. メールに `abc` と入力して送信:メールのエラーが出る。
3. 内容に `あ` と入力して送信:10文字以上のエラーが出る。
4. 名前にスペースだけを入力して送信:名前のエラーが出る。
5. 正しく入力して送信:確認完了のメッセージが出て、入力欄が空に戻る。

## ステップ4:Slack通知の処理

チェックを通過した内容を、Slackに通知する。

### 4-1. 作ったもの

| ファイル | 内容 |
|---|---|
| `src/lib/slack.ts`(新規) | Slackに通知を作って送る関数 `sendSlackNotification` |
| `src/app/actions.ts` | チェック通過後に、Slack通知を呼び出す。失敗時のエラー処理を追加 |
| `src/lib/contact-schema.ts` | 全体のエラー用に `formError` を追加 |
| `src/components/contact-form.tsx` | 全体のエラー表示を追加し、成功メッセージを本番用に変更 |

### 4-2. 通知の仕組み

**Slack Incoming Webhook** は、発行されたURLに、JSONを **POST** すると、決めたチャンネルにメッセージが投稿される仕組みである。このプロジェクトでは、サーバー側(Server Action)から `fetch` でPOSTしている。

通知は、**Block Kit** という形式で整形した。

| 部分 | 内容 |
|---|---|
| `header` | 見出し「新しいお問い合わせ」 |
| `section` の `fields` | お名前、メールアドレス、送信日時を2列で並べる |
| `section` の `text` | お問い合わせ内容 |
| 最上位の `text` | スマートフォンの通知など、整形表示が使えない場所に出る代わりの文章 |

### 4-3. 通知の設計(「誰が見て何をする通知か」)

- **見る人**:総務の担当者。
- **含める項目**:お名前、メールアドレス、送信日時、お問い合わせ内容。
- **メンション**:付けない。チャンネルに投稿されるだけにした。
- **依頼文**:入れない。「何をするか」は、担当者の判断に任せた。

### 4-4. ユーザーの入力をエスケープする理由

Slackの文章では、`&`、`<`、`>` が特別な意味を持つ。例えば、`<!channel>` と書くと、チャンネル全員へのメンションになる。ユーザーの入力をそのまま送ると、悪意のある入力や、偶然の入力で、意図しない全員通知や、リンクの埋め込みが起きる。

そこで、送る前に次のように置き換える(**エスケープ**)。

| 元の文字 | 置き換え後 |
|---|---|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |

### 4-5. 外部サービスとの通信は「失敗する」前提で作る

| 対策 | 内容 |
|---|---|
| `response.ok` | Slackが成功(HTTPステータスが200番台)を返したかを調べる。違えば、エラーを投げる |
| `AbortSignal.timeout(10_000)` | Slackが応答しないとき、10秒で諦める。いつまでも待ち続けない |
| `try ... catch` | 通知が失敗しても、アプリ全体が止まらないようにする |
| 画面のエラー表示 | 失敗したのに「成功」と見せない。入力内容は残して、もう一度送れるようにする |
| ログには `error.message` だけ | 詳しい原因は、サーバーのログにだけ残す。URLなどの秘密情報が混ざらないようにする |

### 4-6. 送信日時を日本時間にする

Vercelなどのサーバーは、日本時間ではない(UTCのことが多い)。何も指定しないと、Slackの通知の時刻が、9時間ずれる。そのため、`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を指定した。`hourCycle: "h23"` は、0時を「24時」と表示しないための指定である。

### 4-7. 動作確認の結果

- 画面に、成功メッセージが出て、入力欄が空に戻った。
- Slackに、見出し、お名前、メールアドレス、送信日時、お問い合わせ内容が、意図したとおりに並んだ通知が届いた。
- 送信日時は、Slack上の時刻と一致していた。
- エスケープの動作は、半角の `&` `<` `>` を入れて、ステップ6で確認する。

## ステップ5:環境変数でWebhook URLを管理

### 5-1. 作ったもの

| ファイル | 内容 | Git |
|---|---|---|
| `.env.example`(新規) | Webhook URLを入れる場所を示した、中身が空のひな形 | 入れる |
| `.env.local`(PCで作成) | 本物のWebhook URLを入れるファイル | **入れない** |
| `.gitignore`(更新) | `!.env.example` を追加 | 入れる |

### 5-2. 環境変数を使う理由

Webhook URLを知っている人は、誰でも、そのSlackチャンネルに投稿できる。コードに直接書いてGitに入れると、リポジトリを見られるだけで、URLが漏れる。そこで、コードの外にある環境変数に入れて、コードからは `process.env.SLACK_WEBHOOK_URL` で読み取る。

### 5-3. `NEXT_PUBLIC_` を付けない理由

Next.jsでは、環境変数の名前が `NEXT_PUBLIC_` で始まると、ブラウザ側のコードにも公開される。Webhook URLは、サーバー側(Server Action)でしか使わないので、`NEXT_PUBLIC_` を付けない。これで、URLはブラウザには届かない。

### 5-4. `.gitignore` の `!` の意味

もとの `.gitignore` には、`.env*`(`.env` で始まるファイルをすべて無視する)があった。これだと、ひな形の `.env.example` も無視される。`.env*` の下に `!.env.example` と書くと、「これだけは例外として、無視しない」という意味になる。

### 5-5. Gitに入っていないことの確認

| 確認 | 結果 |
|---|---|
| `git status` | `.env.local` が、変更にも未追跡にも出ない |
| `git check-ignore -v .env.local` | `.gitignore:34:.env*` と表示され、無視されていると分かる |

### 5-6. 環境変数を変えたら、開発サーバーを再起動する

環境変数は、開発サーバーの**起動時に**読み込まれる。`.env.local` を作ったり、変えたりしたあとは、`Ctrl + C` で止めて、`npm run dev` をもう一度実行する。

### 5-7. Slack側の画面は変わることがある

手順書では「From scratch」を選ぶはずが、実際の画面には、「AI agent」「Starter app」「From a manifest」「Blank app」の4つが出ていた。このときは、「空のアプリ」に当たる「Blank app」を選んだ。外部サービスの画面は、予告なく変わるので、手順書と違うときは、画面を見て判断する。

## ステップ6:動作確認

達成基準を、1つずつ、実際に動かして確認した。

### 6-1. 達成基準ごとの確認結果

| 達成基準 | 確認方法 | 結果 |
|---|---|---|
| 空欄送信やメール形式不正でフォームが弾く | 何も入力せず送信、メールに `abc` を入力して送信(ステップ3) | 弾かれ、各欄の下にエラーが出た |
| 送信成功時にSlackチャンネルに通知が届く | 正しい内容を入力して送信 | 画面に成功メッセージが出て、Slackに通知が届いた |
| WebHook URLは環境変数で管理され、リポジトリにコミットされていない | `git status`、`git check-ignore -v .env.local`、`git ls-files` | `.env.local` は無視され、管理ファイルの一覧にも出なかった。`.env.example`(空のひな形)だけが入っている |

### 6-2. 正常系と異常系

動作確認では、うまくいく場合(**正常系**)だけでなく、失敗する場合(**異常系**)も確かめる。正常系だけだと、失敗したときの動きが分からないまま、本番に出てしまう。

### 6-3. 追加で確認した2つ

| 確認 | 方法 | 結果 |
|---|---|---|
| 意図しない全員メンションを防げているか | お問い合わせ内容に `<!channel>`、`<b>太字</b>`、`<https://example.com\|リンク>` を入力して送信 | Slackで、すべて入力した文字のまま表示された。メンション、太字、リンクにならなかった |
| Slackへの通知が失敗したとき | `.env.local` の変数名を、一時的に `SLACK_WEBHOOK_URL_X` に変えて送信 | 画面に赤いエラーが出て、成功メッセージは出なかった。入力内容は残った。ターミナルのログに `Slack通知エラー: 環境変数 SLACK_WEBHOOK_URL が設定されていません` が出た |

### 6-4. 確認のときに気を付けたこと

- **攻撃的な入力は、通知先を確認してから試す**:エスケープが失敗していると、全員にメンションが飛ぶ。テスト用のチャンネルで試した。
- **失敗は、秘密の値を変えずに起こす**:URLそのものではなく、変数の「名前」だけを変えた。URLを画面やログに出さずに済む。
- **画面とログの役割を分ける**:ユーザーには、やさしい文言だけを見せる。詳しい原因は、サーバーのログにだけ残す。ログには、URLなどの秘密情報が出ない。
- **確認のあとは、元に戻す**:変数の名前を元に戻し、開発サーバーを再起動して、通知が届くことを、もう一度確認した。

### 6-5. 気付いたこと

- 成功メッセージの文言を書き換えたときに、句点が2つ(`。。`)になっていた。文言を変えたときは、画面で読み返して確認する。
- 開発サーバーは、環境変数を起動時に読み込む。変数を変えるたびに、再起動が必要だった。

## ステップ7:Vercelへのデプロイ

### 7-1. やったこと

1. 作ったコードを、GitHubのPublic(公開)リポジトリに **push** した。
2. Vercelに、GitHubのリポジトリを **インポート** した。
3. Vercelの画面で、環境変数 `SLACK_WEBHOOK_URL` を登録した(Sensitiveをオン)。
4. 「Deploy」を押して、ビルドと公開が終わるのを待った。
5. 公開されたURLでフォームを送信し、成功メッセージとSlackへの通知を確認した。

### 7-2. デプロイとは

自分のPCで動いているアプリを、インターネット上のサーバーに置いて、誰でも使える状態にすること。これまでの `npm run dev` は、自分のPCの中だけで動いていた。Vercelに置くと、公開URLからどこでも開ける。

Vercelは、GitHubとつなぐと、`main` ブランチに push するたびに、自動でビルドして公開し直してくれる。

### 7-3. 環境変数は、Vercelにも登録が必要

`.env.local` は、Gitの管理対象外にしている。そのため、GitHubにもVercelにも、ファイルは届かない。これは意図した動きで、秘密情報を守るための仕組みである。

その代わりに、Vercelの画面で、同じ名前(`SLACK_WEBHOOK_URL`)の環境変数を登録する。アプリのコードは、`process.env.SLACK_WEBHOOK_URL` で値を読むだけなので、ローカルでもVercelでも、同じコードで動く。

- **Sensitive(鍵のトグル)**:オンにすると、登録後に値が画面やログに表示されなくなる。URLのような秘密情報はオンにする。
- **Production / Preview**:Productionは本番の公開用、Previewはブランチなどの確認用。今回は、どちらも同じテスト用チャンネルに届く設定にした。
- **後から登録・変更したとき**:環境変数の変更は、すでに公開済みのものには反映されない。**再デプロイ**(Redeploy)が必要になる。

### 7-4. Publicリポジトリで気を付けたこと

Publicリポジトリは、世界中の誰でもコードを見られる。そのため、次を守った。

- Webhook URLをコードやコミットに入れない(`.env.local` は `.gitignore` で除外)。
- 環境変数のひな形 `.env.example` は、値を空にして入れる。
- URLをチャットなどにも貼らない。Webhook URLは、知っていれば誰でも投稿できるため、漏れたら無効にして作り直す。

### 7-5. 動作確認の結果

| 確認したこと | 結果 |
|---|---|
| デプロイ(ビルド) | 成功 |
| 公開URLのフォームから送信 | 成功メッセージが表示された |
| Slackのテスト用チャンネル | 通知が届いた |

### 7-6. 今後の改善案(今回は未実装)

- **スパム・連続送信への対策**:公開フォームには、自動プログラムによる大量送信が来ることがある。回数制限(レート制限)や、CAPTCHAなどを検討する。
- **Vercelの無料プラン(Hobby)は、商用利用ができない**:会社のサイトなど、仕事で使う場合は、有料プランなど、利用条件を確認する。
- **本番用のSlackチャンネルへの切り替え**:本番では、通知先を総務の担当チャンネルに変え、Webhookを作り直して、Vercelの環境変数を差し替え、再デプロイする。

## ステップ8:仕上げ(全体の振り返り)

### 8-1. 達成基準の確認

| 達成基準 | 確認方法 | 結果 |
|---|---|---|
| 空欄送信やメール形式不正でフォームが弾く | 空欄、不正なメールで送信 | 達成 |
| 送信成功時にSlackチャンネルに通知が届く | ローカルと、Vercelの公開URLの両方で送信 | 達成 |
| Webhook URLは環境変数で管理され、リポジトリにコミットされていない | `git ls-files` と `git log` で確認 | 達成 |

### 8-2. 全体の流れ

```
ブラウザ(フォーム) → Server Action(zodで検証) → Slack Incoming Webhook → Slackチャンネル
                          ↑
                  環境変数 SLACK_WEBHOOK_URL(.env.local / Vercel)
```

### 8-3. 学んだことの要点

- 入力のチェックは、必ずサーバー側で行う(ブラウザ側は回避できる)。
- 外部から来た文字は、そのまま別のサービスに渡さず、エスケープする。
- 外部サービスとの通信は、失敗する前提で作る。ユーザーにはやさしい文言、ログには原因を残す。
- 秘密情報は、コードに書かず、環境変数で管理する。Gitに入れない、チャットに貼らない。
- うまくいく場合だけでなく、失敗する場合も、実際に動かして確かめる。
